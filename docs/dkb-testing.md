# Testing DKB Recomp

This guide is for running DKB Recomp on your own PC and reporting what happens. You build it from source with your own
copy of the game. Nothing from the game is in this repository, and nothing you build from it may be shared: not the
executable, not the generated code, not the shader cache.

## What you need

- Windows 10 or 11 on an x86-64 CPU with AVX2.
- 16 GB of RAM plus a large page file (32 GB is comfortable). The game commits about 14 GB (13.5 GiB at the start, 13.75 GiB after 40 minutes in the tutorial and first mine,
  rising about 6 MB per minute, peak 15.3 GiB; sessions over an hour are untested), so close other large programs first.
- A GPU with Vulkan 1.3 and a current driver.
- About 15 GB free for the build (the packed RomFS is about 9 GB), besides the space your dump takes.
- *Donkey Kong Bananza* base version 1.0.0 or update 3.2.0 (title version 458752), dumped from your own Switch 2: the
  ExeFS (`main`, `sdk`, `main.npdm`) and the RomFS as a folder, or a `.nup` file. The installer picks the target by the
  `main` hash and, for 3.2.0 only, keeps the generated C and objects in `temp/gen` and `temp/build` so a second install
  does not relift or recompile; the base install removes them. This project does not explain how to dump the game.
  A `.nup` file (the container Eglantine and Eden load) goes straight to the installer (`--nup`, [installer.md](installer.md)).
  For a build by hand, `tools/extract_nup.py` writes the folders: `python tools\extract_nup.py <game>.nup --list` shows
  the packages, and `python tools\extract_nup.py <game>.nup --select latest --out build\extracted\dkb-dump` writes
  `exefs` and `romfs` there as Eglantine runs them (the newest update's ExeFS, the base RomFS with the update's laid
  over it; `--select base` for 1.0.0), checking every file's SHA-256. Pass those two folders to the commands in the
  README, with `dkb458752` and `recomp\patches-dkb458752.txt` in place of `dkb100` for 3.2.0.

On Apple Silicon macOS the same steps work ([building.md](building.md), "macOS"): the commands use
`.venv/bin/python`, the executable is `build/dkb100/dkb`, and the renderer is MoltenVK. The game boots to the mode
select, but the destructible terrain is not drawn yet, because Metal has no geometry stage.

## Build

Install the toolchain from [building.md](building.md) (MSYS2 UCRT64 Clang, Ninja, Python 3.12 in `.venv`, .NET SDK),
then run the commands in the README, "Building from source". The executable ends up in `build\dkb100\dkb.exe`.

The generation command must include `--patches recomp\patches-dkb100.txt`. This enables the controller setup patch
that bypasses the game's HID server proxy, which the host does not implement. If you generated the code without
that argument, rerun the README's generation command with it and then rebuild with `tools\build_game.py`.
Rebuilding alone leaves the unpatched generated code in place and the game stops during controller setup.

## Run

```
build\dkb100\dkb.exe
```

Run it from inside the repository: it finds the shader translator (`build\xlate\totk_xlate.exe`) by looking up from
its own folder. The first run translates every shader it meets and is slow; later runs use the cache.

Prepare the shaders once (the Bananza installer does this as its `dkb_shaders` step): the game's own shader files hold
about 18,800 shader stages, and translating one the first time a draw needs it takes about 35 ms, with the draw waiting.
On a first visit to an area that adds up to seconds. These two steps translate them all up front, from your own game
files:

```
.venv\Scripts\python tools\dkb_shader_census.py --version dkb100 --out build\dkb100
build\dkb100\dkb.exe --prepare-shaders
```

The first reads the shader folders of the extracted RomFS (4 seconds) and writes `seed-nvn2.bin` (about 187 MiB) next to
`dkb.exe`; the second lowers and translates every stage into the shader cache. Each stage is translated with the default
answers (every texture a 2D texture, float vertex inputs and colour outputs), and each vertex stage again for the integer
vertex layouts met so far (Locations 6, 6 and 7, 3 and 4) plus any layout your own `shader-answers.bin` recorded. That
takes about 150 seconds on 20 threads and about 2.9 GB of cache. The pack is deleted afterwards by the installer.
`--prepare-shaders` also builds the driver's pipeline libraries in the same process. The installer instead runs
`--translate-shaders` (translation only) and then `--warm-shaders` (libraries only), so a driver crash in the second
cannot fail the first.

In a cold run of the first area this cut the shaders translated during play from 714 to 62, the worst translation stall
from 6.6 s to 0.34 s, and the 1% low of the last window from 24 to 39 fps. What is left is about 1.4% of the stages the
game loads: 38 embedded in `main` and about 50 whose code is in no file the census reads. They translate on first use, and
play records them. `DKB_ANSWER_STATS=1` logs each translation made in play with what made it necessary.

Useful settings, as environment variables (`set NAME=value` in the same Command Prompt):

| Setting | Effect |
| --- | --- |
| `TOTK_PROFILE_DIR=<folder>` | Use this folder for the save and settings. A new, empty folder gives a fresh start, which is what reports should use. |
| `TOTK_GPU_NAME=<text>` | Use the first GPU whose name contains this text, on machines with more than one. |
| `TOTK_GPU=null` | Run without a picture (no Vulkan). Useful to tell CPU and OS bugs from graphics bugs. |
| `TOTK_XLATE_PROCS=<n>` | Shader translator processes at run time (default 2). Lower it if RAM runs out. |
| `TOTK_TRACE=perf` | Log the frame time, what holds frames back and the GPU time every 60 frames. For stalls and low frame rates. |
| `DKB_WINDOW_FILTER=linear\|catmull_rom\|lanczos\|fsr1` (`window_filter`, also the menu's Window scaling filter row) | How the finished picture is scaled to the window, with any upscaler (`runtime/vk_fsr.c`, `runtime/shaders/win_scale.comp`). Default `fsr1`: AMD FSR 1 where the window is larger than an SDR picture, as before, and nothing else; not set and `upscaler = bilinear`: the plain blit, as before. With `linear`, `catmull_rom` or `lanczos` chosen, `sharpness` sharpens in the same pass at any window size, the output's size included. The log has one `vk: window scaling <filter> from WxH to WxH (sharpness N)` line each time the choice changes. With native HDR (`hdr_native = 1`) the same pass runs in its PQ variant (`win_scale_pq`; the line says `of the game's own HDR picture`) whenever the window differs from the picture or `sharpness` is above 0, with `linear`, `catmull_rom` or `lanczos` chosen; with `fsr1` the HDR picture is blitted as before. With the window the picture's size and `sharpness = 0` the picture is blitted as it is. |
| `DKB_REPLAY_THREADS=N` (or `TOTK_REPLAY_THREADS`, also in the Advanced tab) | Unset, 6 when the process may run on 12 or more logical processors, 4 on 8 to 11 (on AMD only the RX 9070 and 9070 XT, Navi 48 on the proprietary driver, where a Ryzen 7 7700 with an RX 9070 XT ran it without trouble; every other AMD GPU and driver stays off until measured, since a Radeon 610M and a Radeon 890M lost the device with the recorder thread) and off below that (in the Hilltop Layer of Surf Hills on 16, 6 threads gave 45 to 47 fps against 42 with 4), and the command buffer split then defaults to parts of 300 us (`vk_exec.c` `par_threads`; in the layer -101 scene 4 threads gave 57 fps against 53, `docs/dkb-lowend.md`); `0` turns it off (`docs/parallel-replay.md`). A render pass whose targets took at least 256 draws the last time is recorded in slices of 48 to 1024 draws (smaller towards the pass's expected end), each into a secondary command buffer that the pass executes in order (`vk_exec.c` `par_start`, `par_flush`). `N` threads record the slices: the submitting thread and `N-1` workers (`1`: the submitting thread alone, to compare). Try `8` on 16 logical processors. With it set, the helper threads of `TOTK_REPLAY_PAR` take no run. Works with `upscaler = dlss`: the scene DLSS needs is noted from the collected draws. While `TOTK_DUMP` is armed, passes are not sliced. The log says `vk: passes of 256 or more draws are recorded in slices ...` at the first sliced pass, `vk: N replay slice workers started`, and `a sliced pass needed a pass or barrier change inside a slice` when a pass cannot be sliced (it is then left alone). With `N` above 1 the command buffer parts default to at least 300 us (`TOTK_SPLIT_US`, else 1000), so the GPU starts sooner on the sliced passes. |
| `DKB_PAR_DEFER=0` (or `TOTK_PAR_DEFER`) | On by default; `0` makes the end of a sliced pass wait for its slices as before. With sliced passes (`DKB_REPLAY_THREADS`), the end of a sliced pass no longer waits for its slices: the part that holds the pass stays open and the walk goes on while the workers record, up to 2 pass ends at a time by default (`DKB_PAR_DEFER_DEPTH=1..4`; at 4 the Hilltop Layer of Surf Hills ran 9% slower than without the deferral). Before the walk changes anything a held slice reads (a new or revived texture, a first GPU write, an upload, a learned feedback target, a new mirror) it waits for the held slices (`vk_texture.c` `hold_barrier`), and a slice starts only once the slices of earlier passes are recorded (`vk_exec.c` `par_ready`). On the route's Lake Level (3.2.0) it took the replay from 5.96 to 5.44 ms a frame (three interleaved runs each). Without the recorder thread (`TOTK_VK_RECORDER=0`, the default on AMD's proprietary driver) the submitting thread captures the pass end from the part it records itself and makes it there later (`vk_rec.c` `rec_capture_begin_for`), so the deferral works there too. The perf line `sliced passes on the submitting thread` counts the held pass ends and the walk's waits for them; `ab` alternates it with the A/B blocks. |
| `TOTK_CALL_REF=0` | On (`1`) by default: CallCommands and CopyCommands of a recording without deferred binds or pushes record one call to its copy instead of copying the recording into the caller (on Hill about 18,000 calls and 11 ms of the game's main thread a frame). The called copy stays alive while a call names it. Recordings with deferred records are still copied, as before; `0` copies every one. The log counts referenced calls, copied ones and recordings abandoned before EndRecording (whose callees are kept). `nvn_api_cmd.c` `inline_recording`. |
| `TOTK_RESET_CPU_LIST=0`, `=2` | On (`1`) by default: an indirect-reset pointer list is read from guest memory when no GPU write recorded in the same command buffer touches it, instead of submitting the replay so far and waiting for the GPU to read it back (1 to 6 ms of the replay thread per frame on Hill, whose list has about 5,455 entries). `0` always reads it through the GPU; `2` reads both, uses the GPU's and logs every 300 lists how many guest copies differed (`vk: indirect-reset list: ...`; 0 of 900 on Hill). `vk_exec_draw.c` `vk_exec_reset_indirect`. |
| `TOTK_STALL_DUMP=N` | On by default (`5`); `0` turns it off. When no frame has been presented for N seconds after the first 60 frames, a watchdog thread logs the scheduler state as `stall:` lines, then again every 10 s while the stall lasts: each virtual core's owner with its host rip (sampled twice, and whether it is in lifted code), the threads waiting for a core, and every other guest thread's wait (`wkind`, `waddr`, `wobj`, `target`), with priorities, core masks and preempt requests (`kernel.c` `stall_dump`). For hangs: the log then shows what each thread was doing when the game stopped presenting. It only reads under the scheduler lock and reports a lock it cannot get within 200 ms. |
| `TOTK_MEM_REPORT=N` | Logs `mem: commit frame F: guest heap+stack, alias, modules, kernel, other private, mapped, image; process commit (limit)` every N presents (0, the default, off), and once at exit with `exit`. One walk of the address space (`memory.c` `mem_commit_report`), with the GPU side (device-local, mirrors, staging pool, usnap arenas) appended. For where the process's commit goes. Windows only. |
| `TOTK_HEAP_LAZY=0` | On by default (1) since the layer -101 runs (54.3 fps against 53, worst frame about 470 ms against 750), Windows only; `0` commits the whole heap up front as before. For 16 GB machines with a small page file, where the commit limit is what ends the game: the guest heap (the game asks for about 9 GiB with SetHeapSize, about 4.2 GiB of it ever resident) stays reserved and each 64 KiB chunk is committed when first touched (`win32.c` `fault_veh`), or by `mem_touch` before a file read or a Vulkan host-pointer import. See the effect with `TOTK_MEM_REPORT=N`: `process commit` and `guest heap+stack` drop, and a `lazy heap` line counts the commit faults. |
| `DKB_DRAW_PROFILE=1` | Logs where a draw's replay time goes every 60000 draws, in nanoseconds per draw: `vk_exec: draw profile ...` with the sections pass, shaders, pipeline, state, bind-sig, ubo, ssbo, textures, sets, feedback, vertex-buffers, tail and other-ops (`vk_exec_draw.c` `prepare_draw`). For busy areas where `TOTK_TRACE=perf` reports a large `replay avg`. One clock read per section mark, so leave it off otherwise. |
| `TOTK_DYN_UBO=1` | Makes the uniform buffers of the allocated fragment set dynamic (`vk_pipeline.c` `dyn_ubo_convert`), so consecutive draws that differ only in a buffer's offset reuse one written set (`vk_exec_draw.c` `bind_resources`). On by default except on Intel GPUs, where nobody has measured it. Its author measured +16% fps in dense areas on an RTX 3050 laptop; #234's author measured +1 to +2.5 fps on an RX 9070 XT and 12% less replay time on an RTX 3060 Ti; on the -101 heavy scene on an RTX 5060 Ti it is even (56.4 to 57.4 fps against 56.8 to 57.2) and the validation layer reports nothing new. `TOTK_DYN_UBO=0` turns it off. Any value other than `0` (including `off`) turns it on; `ab` alternates it with the A/B blocks. |
| `TOTK_TEX_REPEAT=0` | Looks up every graphics draw's texture descriptors again. By default a draw with the same pipeline as its thread's last descriptor build, the same sampled texture handles, the same descriptor context and generations and the same feedback-layout attachments reuses the descriptors that build wrote (`vk_exec_draw.c` `tex_repeat`); draws that bind storage images always look up. `ab` alternates it with the A/B blocks. For checking a texture glitch against the reuse. |
| `TOTK_CS_BARRIER=game` (or `1`, `ab`) | How consecutive dispatches are ordered (`vk_exec.c` `vk_exec_dispatch_barrier`). Default `0`: a full barrier before every dispatch, as before. While terrain breaks, the game's compute work is long runs of one-wave dispatches (RGP on an RX 9070 XT: 32 threads, about 22 us each, a compute pass of 3.7 ms), and a barrier before each keeps one compute unit busy at a time. `game` (experimental) records no barrier before a dispatch that follows only compute work unless the game asked for one since the dispatch before, as Maxwell orders compute launches only at a barrier: GPU peaks while terrain broke went from 15.8-19.6 ms to 12.3-15.0 ms (Ryzen 7 7700, RX 9070 XT, 26.11.1), with no visible difference in about ten minutes of play. `1` keeps a barrier there but among the compute and transfer stages only, which flushes no colour or depth cache (measured within the spread); `ab` switches `0` and `1` with the A/B blocks. With `TOTK_TRACE=perf` the `perf: dispatches after compute work alone` line counts those dispatches by whether the game put a barrier before them, and `TOTK_TRACE=gfx` counts the compute barriers. |
| `TOTK_LOCK_HOLDS=1` | Diagnostic, with `TOTK_TRACE=perf`: every 60 frames, the callers that held the texture lock over 200 us, as exe offsets for `totk.map`, with their count, total and longest hold. The perf trace always logs the waits over 100 us on the texture, memory pool, mirror and generation-table (`gen_lock`, exclusive takes that query) locks. |
| `TOTK_WB_ASYNC=0` | Makes the replay wait for a deferred guest read's write-back again (`nx2_read_nowait = 1` only). On by default: the render target's copy is submitted without a wait and lands in the storage at a later poll (`vk_texture.c` `vk_texture_wb_poll`), up to a GPU batch later than the waited copy did. The read that queued it is not affected, but a CPU write to the storage in that longer window keeps the CPU's bytes and drops the copy, so that render never reaches the storage. In Canyon Layer (replay-bound, in-launch A/B) the frame interval was 1.2 and 1.8 ms shorter and none of 2,000 late copies were dropped; on a GPU-bound RTX 3050 laptop the gain was within noise and 30-45% were dropped, measured before a fix that may lower that share. The copies are submitted after the texture lock is let go (`vk_texture.c` `vk_texture_wb_poll`), with no switch of its own; that was measured on NVIDIA only. `ab` switches with the A/B blocks. |
| `TOTK_USNAP_FAST=0` | Takes the uniform snapshot of a submission (`vk_usnap.c` `vk_usnap_begin`) the long way, as before. On by default: repeated uniform ranges are skipped when collected, the radix sorts run only the passes the key span needs, repeated GPU writes of one range are merged, and with `draw_merge` the arena gets one copy. The snapshot is the same; in Canyon Layer (in-launch A/B) the frame interval was 0.8 and 0.7 ms shorter. `ab` switches with the A/B blocks. |
| `TOTK_USNAP_DROP_LOCAL=0` | Appends every GPU write the replay notes to the uniform snapshot's list of writes in flight under `drop_lock`, as before. By default a GPU write the replay notes (a storage buffer a draw writes, an inline uniform update, a copy) goes into a list of the noting thread's own, which the next submission's uniform snapshot moves into its list of writes in flight (`vk_usnap.c` `wr_local`, `wr_take`), so the slice workers take `drop_lock` only for a write that drops a uniform copy; the copies a write drops are dropped at once as before, and `vk_usnap_gpu_writing` (the indirect reset's guest read) looks through every thread's list under the list's own lock. In the Hilltop Layer of Surf Hills (3.2.0, in-run A/Bs) the frame interval went from 10.63 and 10.41 ms to 10.30 and 10.08 ms (3.1% in both launches), and with `TOTK_DRAW_MERGE=1` from 9.83, 9.59 and 9.70 ms to 9.73, 9.57 and 9.62 ms (1.0%, 0.2% and 0.8%). `tests/usnap_prune_test.py` checks that the lists give the same writes in flight as the global order. `ab` alternates it with the A/B blocks, per submission. |
| `TOTK_WB_UNLOCKED=0` (or `DKB_WB_UNLOCKED=0`) | Waits for a waited write-back's GPU copy (a CPU read of a render target the GPU wrote, and the write-back at a fence wait) with the texture lock held, as before. By default the copy is queued under the lock, the wait for the GPU happens without it, and the bytes land through the same checks as `TOTK_WB_ASYNC` (`vk_texture.c` `wb_copies`): the lock was held about 0.35 ms per write-back, some 340 times a second in Lake Level, while the replay's texture lookups waited for it. `ab` switches with the A/B blocks. |
| `TOTK_WB_EARLY=0` | Writes every GPU write into a VRAM mirror back to guest memory at the end of the submission, after its last full barrier, as before. By default the write-backs of a part held back by `TOTK_PAR_DEFER` go out once that part is submitted: a thread of its own (`vk_memory.c` `wb_thread`) writes back the ranges of that pass and the ones before it from a command buffer submitted after it, while the walk records the next parts; what no held part's write-back takes still goes back at the end. Only at least 256 KiB at a time; `TOTK_WB_EARLY=<KiB>` above 1 sets another amount. In the Hilltop Layer of Surf Hills the write-backs (about 22.8 MiB a frame) took the GPU about 0.7 ms after its last draw, inside the tail the game's `nvnSyncWait` waits for; with this about 2-3 command buffers a frame took 18.8 MiB of them before the end. There (3.2.0, on 9ed1784, in-run A/Bs, two launches each) the frame interval went from 11.17 and 11.15 ms to 10.50 and 10.45 ms (6.0% and 6.3%), and with `TOTK_DRAW_MERGE=1` from 9.72 and 9.68 ms to 9.71 and 9.67 ms (0.1%), while the replay went from 7.11 and 7.08 ms to 6.75 ms. The perf line's mirror summary counts the command buffers and their MiB as write-backs "before the end". `ab` switches with the A/B blocks. |
| `TOTK_GS_STORAGE_WRITEBACK=1` | Copies the storage buffers the geometry stage writes (the destructible terrain's) back into guest memory at the end of each submission, as every other GPU write. Off by default: they stay in VRAM, where only later GPU draws read them. In the Hilltop Layer of Surf Hills (3.2.0) the copies were 70 MiB and 7.7 ms of GPU time a frame. `ab` alternates it with the A/B blocks. |
| `TOTK_MIRROR_OWN=0` | Copies a page into its VRAM mirror again after the mirror's own GPU write to it has been reported, as before. By default `vk_memory.c` `mirror_sync` leaves out the pages whose newest write is a GPU write the mirror already holds (`vk_gpu_written_into`). In the Hilltop Layer of Surf Hills (3.2.0) those copies were 57 of the 58 MiB a frame the syncs uploaded, and for the geometry stage's storage they put stale guest bytes over the GPU's. `ab` alternates it with the A/B blocks. |
| `TOTK_MIRROR_PRESNAP=<n>` | The longest submission period `vk_memory.c` `vk_mem_mirror_begin` predicts when it snaps the pools the next submission will use, 8 by default: a pool is snapped when the submissions p and 2p before the next one synced it, for some p up to n. `0` snaps the previous submission's pools instead, as before; Bananza's submissions use disjoint pools, so none of those snaps was used (`presnap_wanted`). The `mem: mirror frame` line reports the pools snapped a frame, how many the submission used, and the MiB of the unused ones. Measured on NVIDIA only (RTX 3060 Ti); it applies on AMD and RADV as well, where nobody has measured it. |
| `TOTK_MIRROR_STAGED=<MiB>`, `<KiB>k` or `all` (or `DKB_MIRROR_STAGED`), `TOTK_STAGED_WB=fault\|fence` | Experimental, off by default (`0` or unset). In mirror mode, an imported pool of at least that size (`all`: every lazily imported pool, the small ones too) is never imported for its VRAM mirror: a resolve leaves it unimported, so paths that only read guest memory (the uniform snapshot, the indirect-reset list, counter words) import nothing, and its first buffer use (or copy, fill or update) makes the mirror. The mirror is zeroed on the GPU and gets the pages the write-watch ever saw written (a page never written still holds the zeros it was committed with, and reading the rest cost a page fault each): a pool over 16 MiB from the thread that made it, through 16 MiB staging buffers of the upload batch, each piece submitted at once (`vk_memory.c` `staged_fill`); a smaller one in the prologue of the part that first used it, with that prologue's other staged uploads (`staged_upload`), so the hundreds of small pools a layer's first frame uses cost no submission of their own. After that the prologue copies the written pages from guest memory into staging buffers of at most 16 MiB and from there into the mirror (`staged_upload`). A staged pool that was never imported is released without the GPU wait of `vk_pool_fini` (`TOTK_POOL_FINI_WAIT`): the GPU never touched its storage. With `fault`, a pool released while its mirror still owns GPU-written bytes drops them unfetched (`staged_forget`): the guest storage keeps its older bytes there, where an import would have the GPU's. NVN lets a game read them after `nvnMemoryPoolFinalize`; the read probe on the Hilltop Layer saw no CPU access to the arena's GPU-written bytes at all, and the `mem: frame N: staged pools` line counts the pools and MiB each frame's releases dropped. What the GPU writes into such a pool: with `TOTK_STAGED_WB=fault` (the default) it stays in the mirror; at the submission's fence its pages become `PAGE_NOACCESS`, and the first CPU access, or a host path that hands the pages to the kernel, fetches the GPU's bytes of that 64 KiB block from the mirror and opens the pages (`staged_fetch`, Windows only; elsewhere it falls back to `fence`); later GPU writes to a fetched page go back at the fence. `fence` copies every write-back into guest memory at the fence through a readback buffer (`staged_wb_record`, `staged_wb_done`), which uploads the touched pages again at their next sync. A pool whose mirror is refused (budget, no write watch, allocation, overlap; with `fault` also a mirror that would share a 4 KiB page with another pool), or first used on a `TOTK_REPLAY_PAR` helper thread, is imported after all (`mem: staged pool ... imported after all` for the first 32, and counted by reason). When that import fails as well, the pool is left unbacked, as a pool whose first-use import failed: the draws, binds, copies and indirect resets that reach it are skipped instead of stopping the game (`mem: staged pool ... has neither a mirror nor an import` for the first 32, and counted in the staged lines). Aimed at the 450 MiB terrain arena of each Surf Hills layer, whose import stalled the frame of its first use (#397): try `64`; `all` also takes the about 276 small pools (73 MiB) that frame imported in 36-42 ms, about 0.1 ms of `vkAllocateMemory` each, and the about 215 of each reload. Log: a `mem: staged mirror of N MiB ... first fill` line per `staged_fill` (the first 32); a `mem: frame N: staged pools` line for each frame in which staged pools got a mirror, were imported after all or were released (the first 256: mirrors filled in a prologue with their MiB and CPU copy time, imports by reason, releases and their time); and with the mirror summary a `mem: staged frame` line (uploads, fence write-backs), a `mem: staged pools frame` line with the same totals since the start and the owned bytes released pools dropped unfetched, and, with `fault`, `mem: staged own frame` lines (owned bytes, protection changes, fetches, fetches inside `staged_wb_done`, copy-back pages found owned again; the first 32 fetches get a `mem: staged fetch` line with the host rip, and the first 16 pages `VirtualProtect` refused a line each: their owned bytes are fetched at once and they go to the fence copy-back). `TOTK_MEMORY=verify` skips owned pages and counts them. Ignored, with a line, without the mirror, with shadow storage or with `TOTK_POOL_LAZY=0`. Measured on the Hilltop Layer of Surf Hills (3.2.0, RTX 5090, on 9ed1784, one run each): with `fault` the frame of the layer's first use took 193 ms against 307 ms off, with no fetch and about 0 protection changes a frame after the first; frame rate within the launch spread (68.5 against 69.1 fps). With `fence` every frame got about 3,000 page uploads and 5,000 write-back copy regions, 29-34 fps instead of 54-67 (3 runs off, 4 on). With `all` (same layer and card, on 9ed1784, one run per arm): the frame of the layer's first use took 115-125 ms in four runs (replay 100-111 ms) against 242-280 ms off (replay 227-265, of it 110-118 ms importing 280-287 pools) and 162 ms with `64` (40 ms importing 276 small pools); nothing was imported, and that frame's prologues filled 196 small mirrors (54 MiB, 50 MiB of written pages copied in 3.2 ms of CPU time). Steady state 89.9 fps against 86.5 off and 89.0 with `64`; game threads fetched GPU-owned bytes of small pools 336 times in 80 s, 0.4 ms each on average and 5.7 ms at most. ### Scripted runs without anyone playing

`tools/scenario.py` starts the game from a private save, plays a button script into it and says how the run ended
(completed, crashed, device lost, hung) and whether it was slow, from the frame times (`tools/perf_check.py`). A
scenario is `tests/scenarios/<name>.toml`; its save is a copy of one of your profiles in `build/saves/<name>/` and is
never committed. `tests/scenarios/README.md` says how to make one.

    python tools/scenario.py --list
    python tools/scenario.py tutorial-cave --build build/dkb100 --repeat 3
    python tools/scenario.py tutorial-cave --warp HillLevelStage      start in another stage (tools/save_warp.py)
    python tools/scenario.py tutorial-cave --sweep "LevelStage$"      once per matching stage

`--warp` rewrites the stage in the run's copy of the save, so one save reaches every stage
(`python tools/save_warp.py --stages` lists them). Each run's log, last frame and verdict go to `build/scenarios/`; they
are derived from the game, so keep them out of reports unless you have checked they show nothing of it.

## Add-on content (untested in game)

Nothing in the game has been run with add-on content (DLC) yet: the reader (`runtime/aoc_romfs.c`) is checked on a
synthetic pack (`tests/aoc_romfs_test.py`) and by `--probe-aoc` on a real one, and that is all. Update 3.2.0 is the
same: the installer builds it and it boots, and nobody has played it. If you try either, say so in the report.

The reader looks for `aoc-<index>/` folders next to `dkb.exe` (`<index>` is 0 to 31), each holding `romfs.bin` and
`aoc-index.bin`. The installer writes them when it is given a `.nup` that holds add-on content: each add-on content
package (kind `addon` in `extract_nup.py --list`) with a RomFS becomes `aoc-<n>`, where `<n>` is its title id minus the
application id minus `0x1000` (0 to 31; others are ignored, with a warning), and the install log has one `aoc: index <n>: <files> files`
line per pack. A pack that fails is skipped with a warning; the install goes on. With ExeFS and RomFS folders there is
nothing to read it from, so by hand, from the add-on content's extracted RomFS folder, with `<dlc>` its root and `<n>`
its index:

```
.venv\Scripts\python tools\dkb_pack_romfs.py --dir <dlc> --out build/aoc-pack
.venv\Scripts\python tools\romfs_index.py --romfs build/aoc-pack --out build/aoc-pack/index
mkdir "<exe folder>\aoc-<n>"
copy build\aoc-pack\romfs.bin "<exe folder>\aoc-<n>\romfs.bin"
copy build\aoc-pack\index\romfs-index.bin "<exe folder>\aoc-<n>\aoc-index.bin"
```

`dkb_pack_romfs.py` writes `romfs.bin` and `index.json`; `romfs_index.py` turns those into the TOTKRFS1 file
`romfs-index.bin`, which the reader wants under the name `aoc-index.bin`. Then `dkb.exe --probe-aoc` mounts the first
pack and reads up to 64 files back whole; with `DKB_AOC_SOURCE=<dlc>` it also compares them with the folder.

## Experimental ultrawide mode

Bananza 1.0.0 supports an optional wider horizontal camera view with proportional UI.
The title/main-menu background fills the wider viewport: its wall and atmosphere are
enlarged uniformly and cropped vertically, while the logo and text keep their proportions.
Corner HUD elements, including saving/loading indicators, can move to the screen edges
or remain in a centered 16:9 area. Menu controls and world markers remain centered.

Open F1 → Display → Resolution to set **Render resolution**. The **Ultrawide** section on the Display tab contains the wide view toggle and **HUD position**.
The **Graphics** tab contains **Render Options**, **Color**, and **HDR**.
Ultrawide is off by default; HUD placement defaults to **Screen edges** when enabled.
All three settings currently require a restart. Available resolution presets are:

| Ultrawide | Aspect-ratio group | Presets |
| --- | --- | --- |
| Off | 16:9 | 1280x720, 1600x900, 1920x1080, 2560x1440, 2880x1620, 3840x2160 |
| On | 21:9 class | 2560x1080, 3440x1440, 3840x1600, 5120x2160 |
| On | 32:9 | 3840x1080, 5120x1440 |

The original virtual-display functions return 2880x1620 (16:9); this remains the
default when no resolution is selected. These dimensions do not establish the native
3D rendering resolution or the Switch 2 screen's resolution. Window size controls the
host window separately. Use **Black bars** (`DKB_ASPECT=fit`) to preserve proportions
when the window and game have different aspect ratios.

The installer prepares matching background overlays and both HUD variants for every wide preset automatically.
Rerun setup to add them to an older installation or repair missing/changed overlays; this does not change your
resolution or HUD choice. Select **Centered** under HUD position for the central 16:9 HUD and restart.
If generation fails, setup warns and finishes without new overlays; see the named log and rerun setup to retry.

For a manual build, use the game's patch table and generate matching overlays from your own packed
RomFS (Python 3.14+ has built-in zstd; older Python needs `zstandard`). For 3440x1440, generate both HUD variants:

The commands below default to 1.0.0. Add `--version dkb458752` for 3.2.0: its confirmation-dialog layout and
title-effect archive differ. The installer selects this automatically from the verified ExeFS version.

```powershell
python tools/dkb_wide_layout.py --romfs build/extracted/dkb100-packed/romfs --out build/ultrawide/romfs-patches-3440x1440 --aspect 3440x1440
python tools/dkb_wide_layout.py --romfs build/extracted/dkb100-packed/romfs --out build/ultrawide/romfs-patches-3440x1440-hud-edges --aspect 3440x1440 --hud edges
build/ultrawide/dkb.exe
```

Repeat for each installed ultrawide resolution, placing the folders beside `romfs-index.bin`.
The overlays contain game data and must stay private: manual generation stays under `build/`, while setup uses its
owned build staging folder and copies validated overlays into the installation. Regenerate older overlays or rerun
setup to include the title-background fix; updating the executable alone is insufficient.
Missing edge-HUD overlays fall back to the centered variant with a log message.

Environment equivalents are `DKB_ULTRAWIDE=0|1`, `DKB_OUTPUT_RES=<width>x<height>`,
and `DKB_HUD_POSITION=edges|centered`. Overrides lock the corresponding F1 controls;
otherwise choices are saved in `dkb.ini` (an existing `totk.ini` is copied to it on the first run; `TOTK_*` environment variables still work, and `DKB_*` ones win over them). Turning Ultrawide off allows the 16:9 presets
and skips the wide overlay. Invalid sizes fall back to the original 2880x1620 dimensions.

`scene_res` (`DKB_SCENE_RES`, `auto|full`, read at start, F1 "3D scene resolution") controls the size of the 3D scene.
`auto` keeps the game's own dynamic resolution, which settles at a ratio of 1.5 under emulation, so the scene is
two thirds of the render resolution on each side (1280x720 at 1920x1080) and is then upscaled. `full` (or a ratio from
1.0 to 3.0) patches the controller (main 3c12b4 on 1.0.0) to store that ratio: the scene is drawn at the whole render
resolution (more GPU cost, the render-target pool grows by (1.5/ratio)^2) and the game's upscaler, and so DLSS, is not
dispatched. `dkb.log` says `Bananza resolution: 3D scene ratio ...`.
On update 3.2.0 the game also makes each display's 3D image two thirds of the display (a scale in its render
parameters, read at main 79024), and the ratio divides that image, so the controller alone gives a scene of the
display x 2/3 / ratio: `full` drew 1920x1080 at a 2880x1620 render resolution and stretched it. There `scene_res` also
sets that scale to 1.0 (set `render3d`), so the scene is the render resolution divided by the ratio, as on 1.0.0. A ratio
keeps the upscaler: `scene_res = 1.5` at 3840x2160 draws the scene at 2560x1440 and DLSS outputs 3840x2160
(`dlss: Quality 2560x1440 -> 3840x2160`), where `auto` outputs 2560x1440.

Native anti-aliasing (update 3.2.0): `scene_res = full` with `upscaler = fsr3`, `fsr4` or `dlss` runs that upscaler at
100% (input and output the same size), as FSR 3.1, FSR 4 and DLSS in DLAA mode, which anti-alias the 3D scene alone.
At a full-size 3D the game skips the dispatch of its upscale step (its upscaler level, in the settings at +0x10, is 0
there and 2 at a scaled 3D), so there was nothing for the upscaler to replace. The patch set `dkbnative`
(`recomp/patches-dkb458752.txt`) reads the level as 2 at the two loads of the step (main f_7000325a80), so the
dispatch runs from the 3D to an image of the same size, and `dkb_wide.c` `dkb_native_aa_live` turns the set on while
one of the three upscalers is chosen and the scene ratio in effect is 1.0. The setting is live: the Upscaler row
switches it. `game_upscaler` (`vk_exec_draw.c`) keeps its rule that the output is larger than the input, because an
equal-size dispatch of the same shape is also any post-process pass; only while the set is on does it take an
equal-size dispatch, and only one issued from the wrapper main f_7000325f30 (the return address 0x7000325fc4 on 3.2.0,
`dkb_wide.c` `dkb_native_aa_issued_by`). The three upscalers accept equal sizes: `vk_fsr3.c` and `vk_fsr4.c` check only
that the input is not larger than the output, and `vk_dlss.c` names a scale under 1.1 DLAA. FSR 4 and DLSS are
Windows only, and FSR 3.1 runs elsewhere. The default upscaler (`fsr`, the game's own) and `bilinear` leave `full` as
it was, and 1.0.0 has no `dkbnative` set (no addresses for it yet), so `full` stays as before there. A run with it
has `Bananza resolution: native anti-aliasing on (fsr4 with the 3D at the output size: ...)` in `dkb.log`, then
`upscaler: compute shader ... is taken for the game's upscaler by its images (WxH -> WxH: the same size, native
anti-aliasing, issued at 0x7000325fc4)` and the upscaler's own line at equal sizes (`fsr3: ...`, `fsr4: ...`,
`dlss: DLAA WxH -> WxH, preset K`). The patch set needs the generated code to be made with this `patches-dkb458752.txt`.
The render-target pool is carved from the game's GSys heap, 518144 KiB (506 MiB) in
`System/HeapSize/Product.Nin_Ounce_NVN2.HeapDef.byml.zs`. A pool GSys cannot hold crashed the game before it showed
anything (access violation reading 0xa0 in main+0x128d40 on 3.2.0): at 3840x2160, pools of 474 MiB ran and 514 MiB
crashed, and so did a 5760x3240 output on `auto` (800 MiB). GSys now grows by what the pool adds to the stock
200 MiB, as TotK's texture heap does (`resolution: HeapDef GSys ... KiB` and a `RomFS overlay` line in `dkb.log`),
and the application pool by the same amount, so no other heap shrinks. On 3.2.0 at 3840x2160, `full` (802 MiB),
`1.25` (514 MiB) and 5760x3240 on `auto` (800 MiB) run. When the table cannot be rewritten, `scene_res` keeps the
pool within 474 MiB instead, raising the ratio as far as needed, and says so.

5120x1440 (32:9) and 3840x2160 used to fail during render-resource creation because the game's
render-target pool is a fixed 200 MiB; a patch grows it with the output size. Both now run on 1.0.0
on an RTX 5060 Ti (short runs); 3840x2160 also runs on update 3.2.0 (pools of 356 MiB, 90 s at 60 fps).
5120x1440 on 3.2.0 and other GPUs are untested.

## Mods

Loose replacement files go in a `mods` folder next to `dkb.exe`; no manifest is needed. A file's path below `mods`
is its RomFS path (`mods/Sound/Resource/Foo.bwav` replaces `Sound/Resource/Foo.bwav`), so the folders mirror the RomFS
root. A path the RomFS has is replaced, one it lacks is added. Compressed files (`.zs` and the like) must keep the
game's own format. The files are not checked against anything: a mod that breaks the game is the mod's problem. The
log shows `RomFS mods: N files from ... (R replace, A add)`. `TOTK_ROMFS_MODS` (`romfs_mods` in `totk.ini`) names
another folder, and `TOTK_ROMFS_MODS=0` turns mods off. A folder with a `manifest.tsv` is still read as a checked
overlay.

## What to report

Open an issue with the issue form, or comment on [#3](https://github.com/Lucas-blip-png/dkb-pc-recomp/issues/3)
(GPU testing):

- the release you downloaded, or the commit you built (`git rev-parse --short HEAD`), and the game version (1.0.0 or
  3.2.0);
- GPU, driver version and operating system;
- how far the game got and what you did just before it stopped;
- the log, `logs\dkb.log` next to `dkb.exe` (`logs\totk.log` in builds before the rename), as an attachment. After a crash, copy it before you start the game
  again: the next run renames it to `dkb.1.log`.

Never attach game files, keys, builds or the shader cache, and never paste key values into a log or an issue.
A crash also writes a minidump, `logs\crash-<pid>-<tick>.dmp` (the log's `minidump:` line names it; the newest five
are kept). It holds memory of the game's threads, so it stays on your PC: never attach it to an issue, and send it only
privately when a developer asks for it.
